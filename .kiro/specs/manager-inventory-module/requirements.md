# Requirements Document

## Introduction

The Manager Inventory Module provides a comprehensive inventory management system where the Manager acts as the central validator and encoder for all official records including Purchase Orders (PO), deliveries, and pricing. This module orchestrates the complete inventory lifecycle from Staff-initiated stock requests through Manager validation to Admin approval, ensuring accurate product data, proper replenishment workflows, and delivery compliance. The Manager serves as the critical validation layer between Staff requests and Admin approvals, maintaining accountability and transparency across all inventory operations.

## Glossary

- **Manager**: The user with manager role privileges who validates and encodes all official inventory records (PO, deliveries, pricing)
- **Staff**: The user with staff role who initiates stock requests by clicking the Stock Request button
- **Admin**: The user with admin role who reviews and finalizes Purchase Orders and approvals
- **Product**: An item in inventory including Fuel products and Merchandise products
- **Fuel_Product**: A fuel type product with unit cost and selling price per liter
- **Merchandise_Product**: A non-fuel inventory product with unit cost and selling price
- **Stock_Request**: A replenishment request generated by Staff or Manager indicating low or out-of-stock items
- **PO**: Purchase Order - an official document encoding supplier, item/fuel type, quantity, and cost for procurement
- **Delivery**: A record of received goods from a supplier, validated against the corresponding PO
- **Pending_Request**: A Stock Request in Pending status awaiting Manager validation
- **Validated_Request**: A Stock Request that has been reviewed, adjusted, and set to Validated status by Manager (stock_requests.status = 'Validated')
- **Expected_Deliveries**: A list of deliveries that Staff can view after Admin prints a PO
- **Inventory_History**: A complete audit trail showing the lifecycle of requests from Pending → Approved → Completed
- **System**: The Manager Inventory Module software system
- **Database**: The persistent storage system for inventory, products, requests, POs, and deliveries

## Requirements

### Requirement 1: Product and Pricing Management

**User Story:** As a Manager, I want to encode and update Fuel and Merchandise products with accurate cost and pricing data, so that Admin can review and approve product information for use across the system.

#### Acceptance Criteria

1. WHEN the Manager accesses the Product Management interface, THE System SHALL display all Fuel_Product records and Merchandise_Product records for the Manager's station
2. WHEN the Manager selects a Fuel_Product, THE System SHALL allow encoding of unit cost per liter and selling price per liter
3. WHEN the Manager selects a Merchandise_Product, THE System SHALL allow encoding of unit cost and selling price
4. WHEN the Manager updates a product's unit cost or selling price, THE System SHALL save the changes to the Database with timestamp and Manager user ID
5. WHEN the Manager assigns or updates a product category, THE System SHALL save the category assignment to the Database
6. WHEN the Manager saves product changes, THE System SHALL mark the product data as pending Admin approval
7. WHEN Admin approves the product changes, THE System SHALL make the updated product data visible system-wide
8. THE System SHALL validate that selling price is greater than or equal to unit cost before allowing save
9. THE System SHALL validate that unit cost and selling price are positive decimal values
10. FOR ALL Fuel_Product records and Merchandise_Product records, updating then retrieving the product SHALL return equivalent pricing and category data (round-trip property)

### Requirement 2: Stock Request Validation

**User Story:** As a Manager, I want to review and validate stock requests generated by Staff, so that I can ensure correct quantities before Purchase Orders are issued.

#### Acceptance Criteria

1. WHEN Staff clicks the Stock Request button, THE System SHALL auto-generate a Pending_Request for all items with stock level at or below reorder level
2. WHEN a Pending_Request is created, THE System SHALL set the request status to Pending
3. WHEN the Manager accesses the Stock Request Validation interface, THE System SHALL display all Pending_Request records with item name, current stock level, reorder level, and suggested quantity
4. WHEN the Manager selects a Pending_Request, THE System SHALL allow encoding and adjustment of quantity or liters
5. WHEN the Manager approves a Pending_Request, THE System SHALL update the request status to Validated (stock_requests.status = 'Validated') and record the Manager user ID (manager_id) and timestamp (processed_at)
6. WHEN the Manager rejects a Pending_Request, THE System SHALL update the request status to Rejected and require a rejection reason
7. WHEN the Manager adjusts quantity on a Pending_Request, THE System SHALL save the adjusted quantity to approved_quantity field and log the original requested_quantity for audit purposes via stock_request_audit table
8. THE System SHALL validate that adjusted quantity is a positive integer value
9. THE System SHALL prevent approval of requests with zero or negative quantity
10. WHEN a request status changes from Pending to Validated, THE System SHALL make the Validated_Request available for PO generation

### Requirement 3: Purchase Order (PO) Issuance

**User Story:** As a Manager, I want to encode and generate Purchase Orders based on validated stock requests, so that Admin can review and print official procurement documents that serve as the basis for expected deliveries.

#### Acceptance Criteria

1. WHEN the Manager accesses the PO Issuance interface, THE System SHALL display all Validated_Request records available for PO creation
2. WHEN the Manager creates a new PO, THE System SHALL require encoding of supplier name (from suppliers table), item or fuel type, quantity, and unit cost
3. WHEN the Manager selects a Validated_Request, THE System SHALL auto-populate PO fields with request data including item, quantity, and last known cost
4. WHEN the Manager saves a PO, THE System SHALL assign a unique PO number and set status to Draft
5. WHEN the Manager generates a draft PO document, THE System SHALL create a printable PDF containing supplier, items, quantities, costs, and total amount
6. WHEN Admin reviews a draft PO, THE System SHALL allow Admin to approve or reject the PO
7. WHEN Admin approves a PO, THE System SHALL update the PO status to Approved and record the approval timestamp (approved_at) and approver (approved_by)
8. WHEN Admin prints an approved PO, THE System SHALL update the PO status to Official (matching existing enum values: Draft, Pending Approval, Approved, Official) and record the print timestamp
9. WHEN Admin prints a PO, THE System SHALL automatically create Expected_Deliveries records visible to Staff in their Expected Deliveries tab
10. THE System SHALL link Expected_Deliveries to the issued PO using PO number as reference
11. THE System SHALL validate that PO quantity matches the Validated_Request quantity or Manager adjustment
12. THE System SHALL prevent duplicate PO creation for the same Validated_Request
13. THE System SHALL calculate total PO amount as sum of (quantity × unit cost) for all line items
14. THE System SHALL store PO records in purchase_orders table with existing fields: id, po_number, station_id, supplier_id, status (Draft/Pending Approval/Approved/Official), created_by (Manager), approved_by (Admin), approved_at, total_amount, remarks, expected_delivery_date
15. THE System SHALL store PO line items in purchase_order_items table with existing fields: id, po_id, product_id, item_name, quantity, unit_price, total_price
16. FOR ALL PO records, encoding then printing then parsing the PO document SHALL produce equivalent supplier, item, quantity, and cost data (round-trip property)

### Requirement 4: Fuel and Merchandise Deliveries Validation

**User Story:** As a Manager, I want to encode and validate deliveries against Purchase Orders and integrate with the existing fuel_deliveries workflow, so that I can ensure delivery compliance and handle discrepancies accurately.

#### Acceptance Criteria

1. WHEN a delivery arrives at the station, THE Staff SHALL be able to create a new Delivery record with status Pending (reusing existing fuel_deliveries table for fuel products)
2. WHEN Staff creates a Delivery record, THE System SHALL require adding po_reference field (ALTER TABLE fuel_deliveries ADD COLUMN po_reference VARCHAR(50)) to link to PO number
3. WHEN Staff links a Delivery to a PO, THE System SHALL display the PO expected quantities for all items from purchase_order_items table
4. WHEN Staff encodes delivery quantities, THE System SHALL allow encoding actual received quantity or liters for each item (existing fuel_deliveries.delivery_liters for fuel, new merchandise_deliveries table for merchandise)
5. WHEN Manager reviews a delivery with Pending status, THE System SHALL compare delivered quantity with PO quantity and calculate variance
6. WHEN delivered quantity matches PO quantity exactly (variance = 0), THE System SHALL mark the delivery line item as Compliant
7. WHEN delivered quantity differs from PO quantity (variance ≠ 0), THE System SHALL calculate the variance and mark the delivery line item as Discrepancy
8. WHEN the Manager verifies a delivery with no discrepancies, THE System SHALL update delivery status from Pending to Verified (existing fuel_delivery_operations workflow)
9. WHEN the Manager verifies a delivery with discrepancies, THE System SHALL require encoding variance notes (add variance_notes field to fuel_deliveries) before status can be updated to Verified
10. WHEN Admin finalizes a Verified delivery, THE System SHALL update inventory stock levels by adding the delivered quantities (add finalized_by field to track Admin user, reuse existing fuel_delivery_operations finalize logic)
11. WHEN Admin finalizes a delivery, THE System SHALL update the linked PO status to Received (existing enum value) if all items received or Partially_Delivered (if some items pending)
12. WHEN a Delivery is finalized, THE System SHALL log the PO quantity, delivered quantity, variance, and Manager variance_notes via log_fuel_inventory_action (fuel) or inventory_transactions (merchandise)
13. THE System SHALL validate that delivered quantities are non-negative decimal values
14. THE System SHALL prevent finalization of deliveries with unresolved discrepancies unless Manager provides variance_notes
15. THE System SHALL extend fuel_deliveries table with new columns: po_reference VARCHAR(50), variance_notes TEXT, finalized_by INT(11), finalized_at DATETIME, and update supplier field to supplier_id INT(11) for referential integrity
16. THE System SHALL create merchandise_deliveries table with columns: id, station_id, supplier_id, delivery_date, po_reference, invoice_no, received_by (Staff), verified_by (Manager), finalized_by (Admin), notes, variance_notes, status (Pending/Verified/Finalized/Rejected), created_at
17. THE System SHALL create merchandise_delivery_items table with columns: id, delivery_id, product_id, po_quantity, delivered_quantity, variance, unit_price, line_total
18. FOR ALL Delivery records, encoding delivery data then retrieving SHALL return equivalent PO link, item quantities, and variance calculations (round-trip property)

### Requirement 5: Inventory History and Audit Trail

**User Story:** As a Manager, I want to access the complete inventory lifecycle from Pending through Approved to Completed, so that I can review and audit all validated and encoded requests for accountability and transparency.

#### Acceptance Criteria

1. WHEN the Manager accesses the Inventory_History interface, THE System SHALL display all Stock_Request records with status Pending, Validated (not Approved), or Rejected
2. WHEN the Manager filters by status, THE System SHALL display only records matching the selected status
3. WHEN the Manager views a Stock_Request in Inventory_History, THE System SHALL display request ID, item name, requested quantity, approved quantity, Manager user ID, approval timestamp, and current status
4. WHEN the Manager views a PO in Inventory_History, THE System SHALL display PO number, supplier, items, quantities, unit costs, total amount, creation date, and status
5. WHEN the Manager views a Delivery in Inventory_History, THE System SHALL display delivery ID, PO number, items, expected quantities, delivered quantities, variances, Manager notes, and confirmation date
6. WHEN the Manager exports Inventory_History, THE System SHALL generate a CSV or PDF report containing all visible history records with timestamps and user IDs
7. THE System SHALL record all status transitions for Stock_Request records including timestamps and user IDs performing the transition
8. THE System SHALL record all Manager edits to quantity, pricing, or delivery data including before and after values
9. THE System SHALL prevent deletion or modification of historical records older than the current business day
10. WHEN the Manager searches Inventory_History by date range, THE System SHALL return all records with creation or update timestamps within the specified range
11. THE System SHALL display Inventory_History in reverse chronological order by default (most recent first)

### Requirement 6: Role-Based Access and Permissions

**User Story:** As the System, I want to enforce role-based access controls for the Manager Inventory Module, so that only authorized users can perform validation, encoding, and approval actions.

#### Acceptance Criteria

1. WHEN a user with role other than Manager attempts to access the Manager Inventory Module, THE System SHALL deny access and redirect to the user's dashboard
2. WHEN a Manager logs in, THE System SHALL grant access only to inventory data for the Manager's assigned station
3. WHEN Admin reviews PO or product approvals, THE System SHALL allow Admin to approve or reject Manager submissions
4. WHEN Staff views Expected_Deliveries, THE System SHALL display only deliveries linked to POs that Admin has printed
5. THE System SHALL prevent Staff from editing or deleting Stock_Request records after Manager validation
6. THE System SHALL prevent Manager from approving their own product pricing changes (Admin approval required)
7. THE System SHALL log all access attempts to the Manager Inventory Module including user ID, timestamp, and access result
8. WHEN a Manager session expires, THE System SHALL require re-authentication before allowing further inventory operations

### Requirement 7: Notification and Workflow Triggers

**User Story:** As a user in the inventory workflow (Staff, Manager, Admin), I want to receive timely notifications when actions are required or completed, so that I can respond promptly and keep the inventory process moving.

#### Acceptance Criteria

1. WHEN Staff creates a Pending_Request, THE System SHALL send a notification to the assigned Manager with request details
2. WHEN Manager approves a Stock_Request, THE System SHALL send a notification to Admin indicating a PO is ready for review
3. WHEN Admin prints a PO, THE System SHALL send a notification to Staff that Expected_Deliveries have been updated
4. WHEN Manager validates a Delivery with discrepancies, THE System SHALL send a notification to Admin with variance details
5. WHEN Manager rejects a Stock_Request, THE System SHALL send a notification to the requesting Staff with rejection reason
6. WHEN Admin rejects a Manager-submitted PO or pricing change, THE System SHALL send a notification to Manager with rejection reason
7. THE System SHALL include a direct link in each notification to the relevant record or interface
8. THE System SHALL mark notifications as read when the user views the linked record
9. THE System SHALL retain notifications in the Database for at least 30 calendar days

### Requirement 8: Data Integrity and Validation Rules

**User Story:** As the System, I want to enforce data integrity and validation rules across all Manager Inventory Module operations, so that inventory data remains accurate and consistent.

#### Acceptance Criteria

1. THE System SHALL validate that product unit cost and selling price are positive decimal values with up to 2 decimal places
2. THE System SHALL validate that stock request quantities are positive integer values
3. THE System SHALL validate that PO line item quantities match the approved Stock_Request quantities or documented Manager adjustments
4. THE System SHALL validate that delivery quantities are non-negative decimal values
5. THE System SHALL prevent saving a PO with zero line items
6. THE System SHALL prevent confirming a Delivery without a linked PO
7. THE System SHALL prevent Manager from approving a Stock_Request with quantity exceeding supplier maximum order quantity if configured
8. WHEN inventory stock level becomes negative after a transaction, THE System SHALL flag the inventory record for Manager review
9. THE System SHALL validate that PO supplier name matches an entry in the configured supplier list
10. THE System SHALL prevent deletion of PO records that have linked Delivery records
11. THE System SHALL enforce referential integrity between Stock_Request, PO, and Delivery records

### Requirement 9: Reporting and Dashboard Visibility

**User Story:** As a Manager, I want to view summary dashboards and generate reports for inventory operations, so that I can monitor performance and identify issues quickly.

#### Acceptance Criteria

1. WHEN the Manager accesses the Inventory Dashboard, THE System SHALL display count of Pending_Request records awaiting validation
2. WHEN the Manager accesses the Inventory Dashboard, THE System SHALL display count of Draft PO records awaiting Admin review
3. WHEN the Manager accesses the Inventory Dashboard, THE System SHALL display count of Delivery records with discrepancies in the last 7 calendar days
4. WHEN the Manager accesses the Inventory Dashboard, THE System SHALL display total value of approved PO records in the current month
5. WHEN the Manager generates a Stock Request Report, THE System SHALL include request ID, item name, requested quantity, approved quantity, status, and timestamps
6. WHEN the Manager generates a Delivery Variance Report, THE System SHALL include delivery ID, PO number, item name, expected quantity, delivered quantity, variance, and Manager notes
7. THE System SHALL allow exporting reports in CSV format and PDF format
8. THE System SHALL allow filtering reports by date range, status, supplier, and product category
9. WHEN the Manager views the Dashboard, THE System SHALL highlight Pending_Request records older than 24 hours in a warning color

### Requirement 10: Integration with Existing Modules

**User Story:** As the System, I want to integrate the Manager Inventory Module with existing fuel management, merchandise transactions, and admin oversight modules, so that inventory data flows seamlessly across the application.

#### Acceptance Criteria

1. WHEN Manager updates Fuel_Product pricing, THE System SHALL reflect the updated price in the fuel transaction module for new sales
2. WHEN Manager confirms a Merchandise delivery, THE System SHALL update the merchandise inventory stock levels used by the cashier transaction module via station_inventory table
3. WHEN Admin approves a PO, THE System SHALL make the PO data accessible to the Admin deliveries oversight module
4. WHEN Admin finalizes a Fuel delivery, THE System SHALL update the fuel_inventory or station_inventory table (type_id = 1 for fuel) with delivered quantities
5. WHEN Admin finalizes a Merchandise delivery, THE System SHALL update the station_inventory table (type_id != 1 for merchandise) with delivered quantities
6. THE System SHALL use the existing Database connection (db_connect.php) and user authentication mechanisms (require_login from lib.php)
7. THE System SHALL log all Manager Inventory Module activities to the shared activity_logs table using log_activity function
8. THE System SHALL use the existing notification system (notification_system.php) to send workflow notifications
9. WHEN Manager accesses Inventory_History, THE System SHALL include relevant entries from fuel_deliveries, fuel_inventory_logs, inventory_transactions, and purchase_orders tables
10. THE System SHALL validate that station_id in all inventory records matches the Manager's assigned station as stored in the users table
11. THE System SHALL reuse existing fuel_delivery_operations.php for fuel delivery workflow (record_delivery, verify_delivery, finalize_delivery methods)
12. THE System SHALL reuse existing inventory_operations.php for receipt confirmation flow where applicable
13. THE System SHALL integrate stock_requests table from existing schema with columns: id, staff_id, station_id, item_id, item_sku, item_name, item_category, current_stock, requested_quantity, approved_quantity, manager_id, manager_notes, status (Pending/Validated/Rejected), processed_at, created_at, updated_at
14. THE System SHALL integrate suppliers table from existing schema with columns: id, name, contact_person, phone, email, address
15. THE System SHALL use existing products table with type_id = 1 for Fuel_Product and type_id != 1 for Merchandise_Product
